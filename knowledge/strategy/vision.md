# Vision: an Agentic Development and Research Hub

## Destination

The agreed organizing principle is concepts and engineering problems, independent
of any provider, framework, or harness. The public experience has four stable
spaces: **Learn** for concepts, **Build** for implementation and troubleshooting,
**Compare** for product evidence, and **Reference** for exact contracts and
commands. Task journeys such as connect, debug, secure, evaluate, and deploy live
inside the appropriate space instead of competing in the global navigation.
Every mature topic should connect understanding, design alternatives, a working
example, verification, and troubleshooting. This applies equally to assembling
existing tools and developing a harness from scratch. See the
[information architecture research](../research/2026-09-23-learning-experience.md).

The maintainer plans a separate harness repository. Its design can draw on this
research, and its experiments can contribute generalizable findings back. It gets
the same evidence standards as other implementations. See the
[concept-first path](concept-first-path.md) and
[ordered issues](implementation-backlog.md).

Agentic Arena becomes one place where developers and researchers can map the agentic ecosystem, understand tradeoffs, select a stack, reproduce comparisons, and contribute evidence throughout the lifecycle.

The product has three connected parts:

1. **Knowledge:** linked project profiles, concepts, research, recipes, and decision records.
2. **Evidence:** versioned experiments, controlled comparisons, traceable results, and honest limits.
3. **Integration:** adapters and reproducible recipes that connect established tools and benchmarks.

Coverage can be broad while implementation proceeds in focused slices. A catalog entry does not imply an integration or an endorsement.

## Developer journeys

- Starting a project: identify requirements, compare viable stacks, run a minimal example.
- Choosing a framework: examine workflow semantics, recovery, durability, overhead, and provider compatibility.
- Preparing deployment: inspect permissions, identity, execution isolation, observability, and failure behavior.
- Researching a question: find related work, reproduce an experiment, identify confounders, publish artifacts.
- Maintaining a stack: record dependency changes and rerun affected evidence.

## Scope boundaries

Map the entire lifecycle, including model access, orchestration, context and memory, protocols, execution, safety, evaluation, observability, deployment, and developer experience. Use [the map](../maps/ecosystem.md) to make missing coverage visible.

Build focused comparison machinery where the existing harness offers an advantage. Prefer external integrations for large benchmark suites and infrastructure. Avoid an undifferentiated score that combines model quality, framework behavior, and sandbox strength.

## Evidence and success

Every recommendation should lead to a source or experiment. Every experiment should record what changed and what stayed fixed. Every domain should expose a useful question and an honest coverage state.

Track: sourced profiles by domain; profiles past their review deadline; reproducible experiments; independent reproductions; time to first useful comparison; documented unsupported combinations. Do not use repository count or stars as a quality score.

This is the chosen planning direction; it does not change shipped capability claims until milestones land. See [delivery plan](delivery-plan.md) and [decision](../decisions/001-ecosystem-hub.md).
